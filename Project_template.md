# Задание 1. Анализ и планирование

Допущения:
- наладчик оборудования (sensor_support) регистрирует датчик в системе Warmhouse (вызывает метод POST http://localhost:8080/api/v1/sensors)
- в реализации метода PATCH http://localhost:8080/api/v1/:id/value помимо изменения БД Warmhouse, также вызывается АПИ датчика для управления статусом и показателями на реальном датчике

### 1. Описание функциональности монолитного приложения

**Управление отоплением:**

- Пользователи могут регулировать температуру, отключать/включать отопление 
- Система поддерживает изменение температуры и изменение статуса датчика

**Мониторинг температуры:**

- Пользователи могут получать данные о температуре
- Система поддерживает получение температуры:
  - сразу со всех датчиков
  - для датчиков конкретной location
  - для конкретного датчика по его id

**Регистрация и управление данными о датчике в БД:**

- Наладчик оборудования может регистрировать новый датчик, обновлять и удалять данные о датчике
- Система поддерживает:
    - регистрацию нового датчика во внутренней БД
    - обновление данных о датчике
    - удаление данных о датчике
  
### 2. Анализ архитектуры монолитного приложения

- Язык программирования: Go
- База данных: PostgreSQL
- Архитектура: Монолитная, все компоненты системы  находятся в рамках одного приложения.
- Взаимодействие: Синхронное, запросы обрабатываются последовательно.
- Масштабируемость: Ограничена, так как монолит сложно масштабировать по частям.
- Развертывание: Требует остановки всего приложения.

### **4. Проблемы монолитного решения**

- сложнее организовывать совместную работу команд, работающих над разными функциями системы
- сложнее тестировать - при релизе нужно проверять все функции системы, что замедляет поставки
- устойчивость к отказам снижена - например, при большом числе запросов в метод получения данных о всех счетчиках можем забить память и упадет все приложение
- нет гибкого масштабирования

# Задание 4. Создание и документирование API

### 1. Тип API

Типы АПИ:
 - для действий со стороны пользователя используется синхронное АПИ (система возвращает Ok или Accepted): большинство клиентких запросов требуют только обращений во внутреннюю БД - вернем Ok, если требуется поход во внешнюю систему - система зафиксирует запрос и вернет Accepted 
 - для обработки событий с датчиков используется асинхронное АПИ (прием сообщений из kafka) - датчик не ждет response


### 2. Документация API

- [Синхронный АПИ Telemetry Service](./apps/telemetry-service/openapi.yaml) - 2 метода для получения телеметрии
- [Асинхронный АПИ Telemetry Service](./apps/telemetry-service/asyncapi.yaml) - прием событий с датчика
- [Синхронный АПИ Device Service](./apps/device-service/openapi.yaml) - 3 метода - регистрация/удаление датчика и управление показаниями датчика
